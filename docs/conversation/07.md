This is a password-state mismatch. PostgreSQL was initialized before the current `POSTGRES_PASSWORD` was written to `.env`. Changing `.env` afterward does not change passwords already stored for database roles.

Because this self-hosted database is still empty, the cleanest fix is to reinitialize it using the current `.env`.

## 1. Enter the deployment directory

From `personal-supabase`:

```bash
cd deploy/self-hosted
```

Check that the current environment exists:

```bash
test -f .env && echo ".env exists"
```

Do not run the secret generators again.

## 2. Stop the failed stack

```bash
sh run.sh stop
docker compose down -v --remove-orphans
```

The `-v` removes Compose-managed volumes, including internal configuration created with the old password.

## 3. Preserve the failed database directory

Rather than deleting it, move it outside the project:

```bash
mv volumes/db/data ../../../personal-supabase-db-failed
mkdir -p volumes/db/data
```

This is the material destructive step in effect: the active database becomes empty, but the old database directory remains recoverable at:

```text
../personal-supabase-db-failed
```

Because this is a brand-new empty installation, no useful application data should be lost.

If the `mv` command says that the directory does not exist, simply run:

```bash
mkdir -p volumes/db/data
```

## 4. Check the database password format

Do not print the password. Check that it is present:

```bash
grep -q '^POSTGRES_PASSWORD=.\+' .env \
  && echo "POSTGRES_PASSWORD is set"
```

If you manually replaced the generated password, use only letters and numbers for now. Characters such as `@`, `:`, `/`, `#` and `%` require URL encoding when placed inside database connection strings.

## 5. Start from the clean database

```bash
sh run.sh start
```

The database initialization scripts will now create these internal roles using the current `POSTGRES_PASSWORD`:

```text
supabase_auth_admin
supabase_storage_admin
authenticator
supabase_admin
```

Wait for completion, then:

```bash
docker compose ps
```

## 6. Verify the affected services

Check Auth:

```bash
sh run.sh logs auth
```

You should no longer see:

```text
password authentication failed for user "supabase_auth_admin"
```

Press `Ctrl-C` to stop following logs.

Check Storage:

```bash
sh run.sh logs storage
```

You should no longer see:

```text
password authentication failed for user "supabase_storage_admin"
```

Check PostgREST:

```bash
sh run.sh logs rest
```

You should no longer see:

```text
password authentication failed for user "authenticator"
```

The Realtime `invalid_schema_name` error should also disappear because its database initialization can now complete.

## 7. Verify PostgreSQL directly

```bash
docker exec supabase-db \
  psql -U postgres -d postgres \
  -c "
    select rolname
    from pg_roles
    where rolname in (
      'supabase_auth_admin',
      'supabase_storage_admin',
      'authenticator',
      'supabase_admin'
    )
    order by rolname;
  "
```

Expected:

```text
authenticator
supabase_admin
supabase_auth_admin
supabase_storage_admin
```

## 8. Verify the gateway

```bash
curl -i http://localhost:8000/auth/v1/health
```

A successful response confirms that the gateway can reach Auth and Auth can reach PostgreSQL.

Then open:

```text
http://localhost:8000
```

## Why this happened

The password has two forms of state:

```text
.env
  └── password supplied to containers

PostgreSQL data directory
  └── password already assigned to database roles
```

Once PostgreSQL has initialized its data directory, changing `.env` changes only the first side. That produces exactly the collection of `28P01` errors you received.

For an existing database containing valuable data, we would rotate its passwords with the supplied `utils/db-passwd.sh` procedure. Reinitialization is appropriate here only because this installation is new and empty. The official guide discusses this under [setting and changing the database password](https://supabase.com/docs/guides/self-hosting/docker#setting-database-password).
