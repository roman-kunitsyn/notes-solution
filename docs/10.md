We found the exact cause. The first database log line says:

```text
PostgreSQL Database directory appears to contain a database; Skipping initialization
```

So the directory was not actually clean when the new container started. It contains an incomplete PostgreSQL cluster with only `supabase_admin`. Every initialization script was skipped afterward.

We’ll reinitialize once more, but this time start PostgreSQL alone and verify it before starting Supabase services.

## 1. Stop everything

From `deploy/self-hosted`:

```bash
docker compose down -v --remove-orphans
```

Confirm no self-hosted containers remain:

```bash
docker ps -a --filter name=supabase
```

The CLI development containers may appear if they are merely stopped; the fixed-name self-hosted containers should be gone.

## 2. Preserve the incomplete database

Use a new destination name:

```bash
mv \
  volumes/db/data \
  ../../../personal-supabase-db-incomplete-20260827
```

Create a truly empty directory:

```bash
mkdir -p volumes/db/data
```

Verify it:

```bash
find volumes/db/data -mindepth 1 -maxdepth 1 -print
```

This command must print nothing.

Most importantly:

```bash
test ! -e volumes/db/data/PG_VERSION \
  && echo "Database directory is clean"
```

Expected:

```text
Database directory is clean
```

If `find` prints files or directories at this point, stop—do not start Docker.

## 3. Start only PostgreSQL

```bash
docker compose up -d db
```

Do not run `sh run.sh start` yet.

Follow initialization:

```bash
docker compose logs -f db
```

This time you must not see:

```text
Skipping initialization
```

You should see initialization activity and eventually something equivalent to:

```text
database system is ready to accept connections
```

Press `Ctrl-C` after initialization finishes.

## 4. Verify all internal roles

```bash
docker exec supabase-db \
  psql -U supabase_admin -d postgres \
  -c "
    select rolname
    from pg_roles
    where rolname in (
      'postgres',
      'authenticator',
      'supabase_admin',
      'supabase_auth_admin',
      'supabase_functions_admin',
      'supabase_storage_admin',
      'pgbouncer'
    )
    order by rolname;
  "
```

Expected:

```text
authenticator
pgbouncer
postgres
supabase_admin
supabase_auth_admin
supabase_functions_admin
supabase_storage_admin
```

Also verify the internal database:

```bash
docker exec supabase-db \
  psql -U supabase_admin -d postgres \
  -c "select datname from pg_database order by datname;"
```

The result should include:

```text
_supabase
postgres
```

## 5. Start the rest of Supabase

Only after those checks succeed:

```bash
sh run.sh start
```

Then:

```bash
docker compose ps
```

Auth, REST, Storage and Realtime should now stop restarting and transition to healthy/running states.

## 6. Verify the affected connections

```bash
docker compose logs \
  --since 2m \
  auth rest storage realtime
```

There should be no new occurrences of:

```text
Role does not exist
password authentication failed
database "_supabase" does not exist
```

Open Studio again:

```text
http://localhost:8000
```

The earlier dashboard error should disappear.

The critical difference in this recovery is the startup order:

```text
empty data directory
        ↓
start db only
        ↓
verify roles and _supabase
        ↓
start remaining services
```

This prevents us from mistaking a healthy PostgreSQL process for a correctly initialized Supabase database. PostgreSQL was technically healthy before, but it was only a bare, incomplete cluster.
