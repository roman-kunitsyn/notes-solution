Now we have the real root cause:

```text
data directory "/var/lib/postgresql/data" has wrong ownership
```

PostgreSQL requires its data directory to be owned by the Linux `postgres` user. The directory is bind-mounted from macOS through Colima, and its ownership mapping changes between initialization and server startup.

The correct local solution is to store PostgreSQL data in a Docker named volume inside the Colima VM.

## 1. Stop the incomplete database

From `deploy/self-hosted`:

```bash
docker compose down -v --remove-orphans
```

Preserve the failed data:

```bash
mv \
  volumes/db/data \
  ../../../personal-supabase-db-ownership-failed
```

Recreate the now-unused directory so the repository structure remains valid:

```bash
mkdir -p volumes/db/data
```

## 2. Create a Colima override

Create:

```bash
nvim docker-compose.colima.yml
```

Add:

```yaml
services:
  db:
    volumes:
      - supabase-db-data:/var/lib/postgresql/data

volumes:
  supabase-db-data:
```

Docker Compose merges volumes by their container target. Therefore, this replaces only:

```text
./volumes/db/data → /var/lib/postgresql/data
```

The SQL initialization files from `volumes/db/*.sql` remain mounted.

## 3. Enable the override

Open `.env`:

```bash
nvim .env
```

Change:

```dotenv
COMPOSE_FILE=docker-compose.yml
```

to:

```dotenv
COMPOSE_FILE=docker-compose.yml:docker-compose.colima.yml
```

This syntax is correct for macOS/Linux. On Windows, the separator would normally be `;`.

## 4. Validate the merged configuration

```bash
docker compose config --quiet
```

Inspect the database volumes:

```bash
docker compose config \
  | sed -n '/db:/,/^[^ ]/p' \
  | sed -n '/volumes:/,/^[[:space:]]*[a-z]/p'
```

The important result is that `/var/lib/postgresql/data` now uses the named volume, not `./volumes/db/data`.

## 5. Start PostgreSQL alone

```bash
docker compose up -d db
docker compose logs -f db
```

This time initialization should complete without:

```text
wrong ownership
Skipping initialization
```

When you see that the database is ready, press `Ctrl-C`.

## 6. Verify the actual mount

```bash
docker inspect supabase-db \
  --format '{{range .Mounts}}{{println .Type .Source "->" .Destination}}{{end}}'
```

The data mount should now resemble:

```text
volume /var/lib/docker/volumes/.../_data -> /var/lib/postgresql/data
```

It must not point to:

```text
/Users/user/Desktop/.../volumes/db/data
```

## 7. Verify initialization

```bash
docker exec supabase-db \
  psql -U supabase_admin -d postgres \
  -c "
    select rolname
    from pg_roles
    where rolname in (
      'postgres',
      'authenticator',
      'supabase_admin',
      'supabase_auth_admin',
      'supabase_functions_admin',
      'supabase_storage_admin',
      'pgbouncer'
    )
    order by rolname;
  "
```

Also:

```bash
docker exec supabase-db \
  psql -U supabase_admin -d postgres \
  -c "
    select datname
    from pg_database
    where datname in ('postgres', '_supabase')
    order by datname;
  "
```

## 8. Start the complete stack

```bash
sh run.sh start
docker compose ps
```

Then check for new failures:

```bash
docker compose logs \
  --since 2m \
  auth rest storage realtime
```

This time the database initialization should persist correctly because its files live inside Colima’s Linux filesystem, where PostgreSQL ownership and permissions work normally.

Commit `docker-compose.colima.yml`, but do not commit `.env`. The override is useful documentation of the macOS/Colima development environment; on a real Linux VPS, we can use the original bind mount or a proper dedicated disk.
