Now we’ll install the official self-hosted Supabase distribution locally. It will be a separate production-like stack, not the stack managed by `supabase start`.

## 1. Stop the development stack

Your Mac has 16 GB RAM, and two complete Supabase installations may consume too much memory. Stop the CLI stack while preserving its state:

```bash
supabase stop
```

Do not use `--no-backup` this time.

Confirm:

```bash
supabase status
```

## 2. Download the pinned self-hosted release

From the root of `personal-supabase`:

```bash
git clone \
  --depth 1 \
  --branch self-hosted/v0.8.0 \
  https://github.com/supabase/supabase \
  ../supabase-self-hosted-source
```

Create the deployment directory and copy the official Docker configuration:

```bash
mkdir -p deploy/self-hosted

cp -R \
  ../supabase-self-hosted-source/docker/. \
  deploy/self-hosted/
```

Record which release we copied:

```bash
printf 'ref=self-hosted/v0.8.0\n' \
  > deploy/self-hosted/.supabase-version
```

The structure should now look approximately like:

```text
personal-supabase/
├── supabase/
│   ├── migrations/
│   ├── tests/
│   ├── config.toml
│   └── seed.sql
└── deploy/
    └── self-hosted/
        ├── docker-compose.yml
        ├── .env.example
        ├── run.sh
        ├── reset.sh
        ├── utils/
        └── volumes/
```

This release pin comes from the current [official self-hosting guide](https://supabase.com/docs/guides/self-hosting/docker).

## 3. Create the private environment file

```bash
cd deploy/self-hosted
cp .env.example .env
```

Confirm that `.env` is ignored:

```bash
git check-ignore .env
```

Expected output:

```text
deploy/self-hosted/.env
```

If the command prints nothing, do not commit anything yet. Add this line to the root `.gitignore`:

```gitignore
deploy/self-hosted/.env
```

Never commit `.env`: it will contain database passwords, signing keys and privileged API keys.

## 4. Generate proper secrets

Run the official generators:

```bash
sh utils/generate-keys.sh
sh utils/add-new-auth-keys.sh
```

The first script generates database and internal service secrets. The second adds the current asymmetric Auth keys and API keys.

Inspect the available credentials:

```bash
sh run.sh secrets
```

Do not paste that output publicly or commit it.

## 5. Configure local URLs

Open:

```bash
nvim .env
```

Find and set these values:

```dotenv
SUPABASE_PUBLIC_URL=http://localhost:8000
API_EXTERNAL_URL=http://localhost:8000/auth/v1
SITE_URL=http://localhost:3000
ADDITIONAL_REDIRECT_URLS=
```

For this local experiment, `SITE_URL` represents the future Notes frontend. Nothing needs to run on port `3000` yet.

Also inspect:

```dotenv
DASHBOARD_USERNAME=
DASHBOARD_PASSWORD=
```

The password generator should already have assigned a strong password. Do not replace it with the example value.

Because logs and analytics are disabled in the new default self-hosted configuration, we should not encounter the earlier Colima `vector` socket problem.

## 6. Validate the Compose configuration

```bash
docker compose config --quiet
```

No output means the Compose configuration is valid.

View the services without exposing secrets:

```bash
docker compose config --services
```

You should see services including:

```text
studio
api-gw
auth
rest
realtime
storage
imgproxy
meta
functions
db
supavisor
```

## 7. Pull and start the stack

```bash
docker compose pull
sh run.sh start
```

The first pull may take some time because this is a separate pinned set of production images.

Check all services:

```bash
docker compose ps
```

Healthy services should show statuses similar to:

```text
Up ... (healthy)
```

If startup fails, run:

```bash
sh tests/test-container-logs.sh
```

For an individual service:

```bash
sh run.sh logs db
```

or:

```bash
sh run.sh logs supavisor
```

## 8. Open self-hosted Studio

Open:

```text
http://localhost:8000
```

Use `DASHBOARD_USERNAME` and `DASHBOARD_PASSWORD` from:

```bash
sh run.sh secrets
```

Notice the difference:

| Environment           | Studio                   |
| --------------------- | ------------------------ |
| CLI development stack | `http://127.0.0.1:54323` |
| Self-hosted stack     | `http://localhost:8000`  |

The self-hosted gateway also exposes:

```text
REST       http://localhost:8000/rest/v1/
Auth       http://localhost:8000/auth/v1/
Storage    http://localhost:8000/storage/v1/
Functions  http://localhost:8000/functions/v1/
```

## 9. Inspect the new database

Connect directly inside the Postgres container:

```bash
docker exec -it supabase-db \
  psql -U postgres -d postgres
```

Inside `psql`:

```sql
select version();
\dt public.*
```

At this moment, our Notes tables should not exist. That is correct: we have created a clean self-hosted Supabase installation but have not deployed application migrations yet.

Exit:

```text
\q
```

## 10. Check Git carefully

Return to the project root:

```bash
cd ../..
git status --short
```

Ensure the output does not contain:

```text
deploy/self-hosted/.env
deploy/self-hosted/volumes/db/data/
deploy/self-hosted/volumes/storage/
```

The copied official `.gitignore` should exclude runtime data. Do not commit yet if secrets or database files appear.

At the end of this step we have two distinct environments:

```text
supabase start
    Development stack created by Supabase CLI

deploy/self-hosted/run.sh start
    Production-style stack created by Docker Compose
```

The next step is to deploy `supabase/migrations` into this empty self-hosted database using `supabase db push --db-url`, without manually creating anything in Studio.
