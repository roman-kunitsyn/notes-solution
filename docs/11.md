That single line can be temporary during initialization. The database starts with bootstrap role `supabase_admin`; `postgres` is created later by Supabase migrations.

Do not stop the container yet. Wait about 30–60 seconds, then run:

```bash
docker compose ps db
```

Check whether initialization is still progressing:

```bash
docker compose logs db | tail -100
```

Then inspect the roles using the bootstrap administrator:

```bash
docker exec supabase-db \
  psql -U supabase_admin -d postgres \
  -c "
    select rolname
    from pg_roles
    where rolname in (
      'postgres',
      'authenticator',
      'supabase_admin',
      'supabase_auth_admin',
      'supabase_functions_admin',
      'supabase_storage_admin',
      'pgbouncer'
    )
    order by rolname;
  "
```

Also check whether the internal database was created:

```bash
docker exec supabase-db \
  psql -U supabase_admin -d postgres \
  -Atc "
    select datname
    from pg_database
    where datname = '_supabase';
  "
```

If the roles and `_supabase` now exist, initialization succeeded and the earlier message was just a premature health check. Continue with:

```bash
sh run.sh start
```

If the result still contains only `supabase_admin`, send this output:

```bash
docker compose logs db | sed -n '1,240p'
```

The important part is the beginning of the new initialization log—not the later repeating `postgres does not exist` messages. It will show whether the Supabase image actually ran its internal migration phase or stopped before it.
