Next we create the Linux production Compose override. Its responsibilities are:

- use Docker-managed volumes;
- bind externally reachable ports to localhost only;
- preserve access for a future reverse proxy and SSH tunnel;
- avoid all Colima-specific configuration.

## 1. Check Compose support

The clean port-replacement syntax requires Docker Compose 2.24.4 or later:

```zsh
docker compose version
```

Your current Docker installation should be new enough. If it is older than `2.24.4`, stop here and tell me the version.

## 2. Populate the production override

Open:

```zsh
nvim docker-compose.production.yml
```

Add:

```yaml
# Linux production overrides.
#
# Envoy remains reachable only from the VPS itself. A reverse proxy will
# terminate HTTPS and forward requests to 127.0.0.1:8000.
#
# PostgreSQL pooler ports remain reachable only through localhost, which
# permits administration through an SSH tunnel without exposing PostgreSQL
# to the public Internet.

services:
  api-gw:
    ports: !override
      - "127.0.0.1:8000:8000"

  supavisor:
    ports: !override
      - "127.0.0.1:5432:5432"
      - "127.0.0.1:6543:6543"

  db:
    volumes:
      - supabase-db-data:/var/lib/postgresql/data

  storage:
    volumes:
      - supabase-storage-data:/var/lib/storage

volumes:
  supabase-db-data:
  supabase-storage-data:
```

The volume entries replace mounts with the same container destination while retaining the database initialization mounts from the base Compose file.

## 3. Validate the combined configuration

```zsh
docker compose \
  --env-file .env.production \
  --file docker-compose.yml \
  --file docker-compose.production.yml \
  config --quiet
```

Render it to a temporary file for inspection:

```zsh
docker compose \
  --env-file .env.production \
  --file docker-compose.yml \
  --file docker-compose.production.yml \
  config \
  > /tmp/supabase-production-compose.yml
```

## 4. Verify the published ports

```zsh
docker compose \
  --env-file .env.production \
  --file docker-compose.yml \
  --file docker-compose.production.yml \
  config |
  sed -n '/published:/,+3p'
```

Every published address should contain:

```text
host_ip: 127.0.0.1
```

There should be no public binding such as:

```text
0.0.0.0:8000
0.0.0.0:5432
0.0.0.0:6543
```

A more direct check:

```zsh
if grep -Eq \
  'host_ip: (0\.0\.0\.0|"0\.0\.0\.0")' \
  /tmp/supabase-production-compose.yml
then
  echo "ERROR: production port exposed publicly"
else
  echo "OK: no port is bound to all IPv4 interfaces"
fi
```

## 5. Verify the persistent mounts

```zsh
grep -A12 '/var/lib/postgresql/data' \
  /tmp/supabase-production-compose.yml

grep -A12 '/var/lib/storage' \
  /tmp/supabase-production-compose.yml
```

Both should be `volume` mounts rather than paths such as:

```text
./volumes/db/data
./volumes/storage
```

You can also ask Compose for the volume names:

```zsh
docker compose \
  --env-file .env.production \
  --file docker-compose.yml \
  --file docker-compose.production.yml \
  config --volumes
```

Expected entries include:

```text
supabase-db-data
supabase-storage-data
```

## 6. Check restart policies

```zsh
docker compose \
  --env-file .env.production \
  --file docker-compose.yml \
  --file docker-compose.production.yml \
  config |
  grep 'restart:'
```

The base Supabase Compose configuration normally provides restart policies. If every service reports an appropriate policy, we do not need to duplicate it in our override.

## 7. Add a convenient production command

Your normal local stack remains:

```zsh
docker compose up -d
```

The future production stack will use:

```zsh
docker compose \
  --env-file .env.production \
  --file docker-compose.yml \
  --file docker-compose.production.yml \
  up -d
```

Do not start that production stack locally yet: it has independent cryptographic keys and expects a fresh production database.

Once the configuration passes, the next local task is creating production scripts for validation, deployment, health checks, backup, and restoration. That will give us a small, repeatable operational interface before we discuss the VPS.
