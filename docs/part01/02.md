Да, полностью убираем импорт старого проекта. Мы создаём новый учебный продукт — `Notes Management System` — и проводим его через весь путь от пустой локальной базы до self-hosted production.

## Обновлённый порядок обучения

1. Создать репозиторий `personal-supabase` — готово.
2. Запустить локальный Supabase stack — готово.
3. Спроектировать чистую модель Notes Management System.
4. Создать migrations, seed и RLS-тесты.
5. Проверить воспроизводимость локальной базы.
6. Получить Linux-сервер для эксперимента.
7. Развернуть официальный self-hosted Supabase через Docker Compose.
8. Развернуть Notes-схему на self-hosted Supabase.
9. Настроить домен, HTTPS, SMTP и secrets.
10. Добавить backup и выполнить пробное восстановление.
11. Добавить CI/CD.
12. Подключить простой клиент: CLI, Telegram-бот или web-интерфейс.

## Шаг 3: модель Notes Management System

Мы сделаем не просто одну таблицу `notes`, а маленькую, но реалистичную систему:

```text
auth.users
    │
    ├── profiles
    ├── notes
    │     └── note_tags
    │             └── tags
    └── attachments → Supabase Storage
```

Первый вариант схемы:

### `profiles`

Публичная информация пользователя:

```text
id          uuid → auth.users.id
username    text
created_at  timestamptz
```

### `notes`

```text
id          uuid
user_id     uuid → auth.users.id
title       text
content     text
is_archived boolean
created_at  timestamptz
updated_at  timestamptz
```

### `tags`

```text
id          uuid
user_id     uuid → auth.users.id
name        text
created_at  timestamptz
```

### `note_tags`

```text
note_id     uuid → notes.id
tag_id      uuid → tags.id
```

Позже добавим приватный Storage bucket для вложений.

## Что изучим на этом примере

Этот небольшой продукт позволит попробовать почти весь основной Supabase:

- PostgreSQL schema;
- migrations;
- Auth;
- Row Level Security;
- REST API через PostgREST;
- Storage;
- generated TypeScript types;
- database functions и triggers;
- seed data;
- local testing;
- deployment;
- backup и restore.

При этом нам пока не нужен frontend. Таблицы и API можно проверять через Studio, `psql` и `curl`.

## Следующие практические шаги

Первую migration создадим только через CLI:

```bash
supabase migration new create_notes_schema
```

Затем напишем в ней таблицы, индексы, foreign keys, trigger для `updated_at` и RLS policies.

После этого:

```bash
supabase db reset
supabase migration list --local
supabase db advisors
```

Отдельной migration создадим Storage bucket и политики:

```bash
supabase migration new create_note_attachments
```

А RLS проверим как минимум для двух пользователей:

- Roman видит и изменяет только свои записи;
- Alice видит и изменяет только свои записи;
- anonymous user не видит никаких приватных записей;
- нельзя изменить `user_id` и передать запись другому пользователю.

Это важнее, чем просто убедиться, что таблица существует.

## Новый смысл шага 8

Старое:

> Перенести существующую базу и Storage.

Новое:

> Применить migrations к пустой self-hosted базе и доказать, что окружение воспроизводимо.

Команда для self-hosted базы будет выглядеть так:

```bash
supabase db push --dry-run --db-url "$SELF_HOSTED_DB_URL"
supabase db push --db-url "$SELF_HOSTED_DB_URL"
```

После этого мы проверим:

```bash
supabase migration list --db-url "$SELF_HOSTED_DB_URL"
```

И выполним API-запрос к серверу. Таким образом, на сервере не будет схемы, созданной руками через Studio: всё восстановится из Git.

## Бесплатный VPS без карты

Здесь неприятная реальность: надёжного долгосрочного бесплатного VPS с root-доступом, 4 GB RAM и без карты практически нет.

Полный Supabase сейчас требует минимум:

| Ресурс |   Минимум | Рекомендовано |
| ------ | --------: | ------------: |
| RAM    |      4 GB |         8 GB+ |
| CPU    |   2 cores |      4 cores+ |
| Disk   | 40 GB SSD |    80 GB+ SSD |

Это текущие официальные требования из [Supabase Self-Hosting Guide](https://supabase.com/docs/guides/self-hosting/docker#system-requirements).

Основные cloud providers запрашивают карту:

- Google Cloud требует платёжный метод даже для Free Trial — это указано в [Google Cloud Free Trial FAQ](https://cloud.google.com/signup-faqs).
- Oracle Cloud обычно требует телефон и банковскую карту — это указано в [Oracle Free Tier documentation](https://docs.oracle.com/iaas/Content/FreeTier/freetier.htm).
- Маленькие бесплатные application-hosting платформы обычно не дают полноценную VM, root-доступ, persistent disk и ресурсы для полного Supabase Compose.

Сайты, обещающие «free VPS, no card», я бы не использовал для базы, secrets или личных данных. У них часто непонятны владелец, ограничения, сохранность данных и условия удаления сервера.

## Как предлагаю поступить

Для обучения нам пока вообще не нужен внешний VPS.

Сначала на твоём Mac:

1. Локально разработать Notes schema.
2. Написать и проверить RLS.
3. Поднять второй, отдельный self-hosted Docker Compose stack.
4. Считать его условным production-сервером.
5. Применить к нему migrations через сетевой connection string.
6. Выполнить backup.
7. Полностью удалить этот self-hosted stack.
8. Восстановить его из Git и backup.

Это даст почти весь опыт настоящего deployment:

```text
Supabase CLI development stack
             ↓ migrations
Self-hosted Docker Compose stack
             ↓ backup
Clean restored stack
```

После этого VPS будет лишь другим Linux-компьютером, доступным через SSH. Мы уже будем понимать, что именно на нём устанавливаем.

Когда дойдём до настоящего интернета, разумнее взять недорогой VPS на один месяц с жёстким spending limit. Для полноценного Supabase следует искать минимум `2 CPU / 4 GB RAM / 40 GB SSD`; 1 GB сервер для полного стека нам не подходит.

Наш непосредственный следующий шаг теперь такой:

> Создать migration `create_notes_schema` с таблицами `profiles`, `notes`, `tags`, `note_tags`, индексами и безопасными RLS policies, затем проверить всё через `supabase db reset`.
