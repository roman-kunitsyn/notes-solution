Yes—for this stage, I recommend one Git repository. But I’m not pushing a giant tightly coupled monorepo. Think of it as one product workspace containing several clearly separated applications.

Why one repository works well now:

- schema and client changes can be committed atomically;
- one migration history remains authoritative;
- one CI workflow can validate the whole system;
- agents can inspect the database contract and client together;
- deployment documentation stays synchronized;
- you are currently the only maintainer.

## Important ownership boundaries

| Directory             | Responsibility                                      |
| --------------------- | --------------------------------------------------- |
| `supabase/`           | Database schema, migrations, RLS and database tests |
| `deploy/self-hosted/` | Supabase infrastructure and operations              |
| `apps/notes-cli/`     | CLI interface and local session handling            |
| `apps/notes-bot/`     | Telegram-specific interface                         |
| `apps/notes-web/`     | Web interface                                       |
| `packages/`           | Proven shared code—not speculative abstractions     |
| `docs/`               | Cross-component decisions and operating procedures  |

The crucial rule is:

> Only `supabase/migrations/` owns the database schema.

The CLI, bot and web client must not contain their own competing schema definitions or execute ad hoc DDL.

## Agent-friendly organization

Use a short root `AGENTS.md`:

```markdown
# Repository instructions

## Architecture

- `supabase/` owns schema, migrations, RLS and database tests.
- `deploy/self-hosted/` owns deployment configuration.
- `apps/` contains independently runnable clients.
- Client applications use only the publishable key.
- Never expose the secret or service-role key.

## Database changes

- Create migrations with `supabase migration new`.
- Never edit an already deployed migration.
- Add or update pgTAP tests for RLS changes.
- Run `supabase db reset`, `supabase test db`, and advisors.

## Dependencies

- Pin dependencies.
- Commit lockfiles.
- Do not introduce shared packages until two consumers exist.

## Validation

Before finishing:

- run tests for the component changed;
- run database tests for schema changes;
- run `git diff --check`;
- report files changed and commands executed.
```

Then put component-specific instructions in nested `AGENTS.md` files.

For example, `apps/notes-cli/AGENTS.md`:

```markdown
# Notes CLI instructions

- Python project managed with uv.
- Typer is the command interface.
- Supabase access belongs in the client layer, not command functions.
- Never store the secret or service-role key.
- Do not send `user_id`; ownership defaults to `auth.uid()`.
- Store sessions outside the repository with restrictive permissions.
- Test commands without requiring the production server.
```

This lets an agent working inside the CLI understand its local rules without loading the entire infrastructure history.

## Rules for parallel agents

If you later use several agents:

- assign directories, not vague features;
- give only one agent ownership of a migration;
- avoid two agents editing the same lockfile;
- let the schema agent finish before client agents consume a changed contract;
- require each agent to report tests and changed files;
- integrate through small commits.

A good split would be:

```text
Agent A → supabase migration and pgTAP tests
Agent B → apps/notes-cli
Agent C → documentation and API examples
Agent D → review/security validation
```

A bad split is two agents independently changing RLS policies or generating migrations.

## When to split repositories

Split only when there is a concrete reason:

- different teams own components;
- components have independent release lifecycles;
- access permissions must differ;
- one application becomes a public/open-source project;
- CI becomes too slow or complicated;
- the infrastructure serves several unrelated products.

You are not there yet. Splitting now would create version coordination without providing a meaningful benefit.

So my recommendation is:

> Keep `personal-supabase` as one product repository, move runnable clients under `apps/`, preserve `supabase/` as the single database authority, and use nested `AGENTS.md` files to give agents narrow working contexts.
