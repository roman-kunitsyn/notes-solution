I recommend building the CLI first using Python, Typer and `supabase-py`.

Why CLI first:

- it matches your CLI-first workflow;
- it is the smallest real client;
- it exercises Auth, RLS and Storage directly;
- its application layer can later be reused by a Telegram bot;
- it avoids frontend complexity while proving the product model.

The first CLI milestone should support:

```text
notes signup
notes login
notes logout
notes whoami

notes list
notes show <note-id>
notes create
notes edit <note-id>
notes delete <note-id>

notes attach <note-id> <file>
notes attachments <note-id>
notes download <note-id> <filename>
notes detach <note-id> <filename>
```

Proposed structure:

```text
clients/notes-cli/
├── pyproject.toml
├── uv.lock
├── README.md
├── src/
│   └── notes_cli/
│       ├── __init__.py
│       ├── __main__.py
│       ├── cli.py
│       ├── client.py
│       ├── config.py
│       └── session.py
└── tests/
```

Important boundaries:

- only the publishable key goes into the client;
- never embed `SUPABASE_SECRET_KEY` or `SERVICE_ROLE_KEY`;
- note ownership remains server-controlled through `auth.uid()`;
- access tokens are stored locally with restrictive permissions;
- dependencies and `uv.lock` are committed and pinned.

So the immediate task is:

> Scaffold `clients/notes-cli`, connect it to local self-hosted Supabase, and implement `login`, `logout`, `whoami`, and `notes list`.

After that vertical slice works, CRUD and attachments will be straightforward. The Telegram bot can become the second interface over the same client layer.
