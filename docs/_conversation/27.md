The restore rehearsal succeeded. Before moving to production infrastructure, we should verify the restored database, remove only the rehearsal deployment, and return to the original stack.

## 1. Verify restored data

Compare restored counts:

```zsh
psql "$SELF_HOSTED_DB_URL" \
  -Atc "
    select 'users=' || count(*) from auth.users;
    select 'notes=' || count(*) from public.notes;
    select 'objects=' || count(*)
    from storage.objects
    where bucket_id = 'note-attachments';
    select 'migrations=' || count(*)
    from supabase_migrations.schema_migrations;
  "
```

Compare this output with:

```zsh
cat "$BACKUP_DIR/expected-counts.txt"
```

Also verify migration history:

```zsh
supabase migration list \
  --db-url "$SELF_HOSTED_DB_URL"
```

Optionally sign Roman in and read his notes through the REST API. That confirms Auth data, password hashes, JWT issuance, PostgREST, and RLS all survived—not merely the tables.

## 2. Remove only the rehearsal deployment

This deliberately deletes the restored rehearsal volumes, not the original volumes:

```zsh
docker compose \
  --project-name supabase-restore \
  down --volumes
```

Confirm the original volumes still exist:

```zsh
docker volume inspect \
  supabase_supabase-db-data \
  supabase_supabase-storage-data \
  >/dev/null &&
  echo "Original volumes preserved"
```

## 3. Return to the original deployment

```zsh
docker compose up -d
docker compose ps
```

Confirm its mounts:

```zsh
docker inspect supabase-db \
  --format '{{range .Mounts}}{{println .Name "->" .Destination}}{{end}}'

docker inspect supabase-storage \
  --format '{{range .Mounts}}{{println .Name "->" .Destination}}{{end}}'
```

They should reference:

```text
supabase_supabase-db-data
supabase_supabase-storage-data
```
