Excellent. We’ll now deploy the schema through Supavisor’s session-mode connection on port `5432`. We will not include `seed.sql`.

## 1. Return to the project root

From `deploy/self-hosted`:

```bash
cd ../..
```

Confirm the migration exists:

```bash
ls -1 supabase/migrations
```

## 2. Build the self-hosted connection URL

Read the required values from the private `.env` without displaying them:

```bash
SELF_HOSTED_ENV="deploy/self-hosted/.env"

SELF_HOSTED_TENANT_ID="$(
  sed -n 's/^POOLER_TENANT_ID=//p' "$SELF_HOSTED_ENV"
)"

SELF_HOSTED_DB_PASSWORD="$(
  sed -n 's/^POSTGRES_PASSWORD=//p' "$SELF_HOSTED_ENV"
)"
```

Verify both values were found:

```bash
test -n "$SELF_HOSTED_TENANT_ID" \
  && echo "Tenant ID found"

test -n "$SELF_HOSTED_DB_PASSWORD" \
  && echo "Database password found"
```

Build the URL:

```bash
SELF_HOSTED_DB_URL="postgresql://postgres.${SELF_HOSTED_TENANT_ID}:${SELF_HOSTED_DB_PASSWORD}@127.0.0.1:5432/postgres"
```

Do not print this variable because it contains the database password.

The username has this special Supavisor format:

```text
postgres.<tenant-id>
```

## 3. Test the connection

First ensure Supavisor is healthy:

```bash
cd deploy/self-hosted
docker compose ps supavisor
cd ../..
```

Then connect:

```bash
psql "$SELF_HOSTED_DB_URL" \
  -c "
    select
      current_database(),
      current_user,
      version();
  "
```

If this works, the CLI should be able to use the same connection.

We’re using port `5432`, Supavisor session mode. Port `6543` is transaction mode and is unsuitable for administrative operations involving session state or prepared statements. The [official connection guide](https://supabase.com/docs/guides/self-hosting/accessing-postgres) documents this distinction.

## 4. Inspect migration state before deployment

```bash
supabase migration list \
  --db-url "$SELF_HOSTED_DB_URL"
```

The local migration should appear only in the `LOCAL` column because it has not yet been deployed.

## 5. Perform a dry run

```bash
supabase db push \
  --dry-run \
  --db-url "$SELF_HOSTED_DB_URL"
```

Expected output should identify:

```text
<timestamp>_create_notes_schema.sql
```

It must not mention:

```text
supabase/seed.sql
```

Do not add `--include-seed`.

## 6. Apply the migration

```bash
supabase db push \
  --db-url "$SELF_HOSTED_DB_URL"
```

Confirm when prompted.

The CLI will:

1. Create `supabase_migrations.schema_migrations`.
2. Execute `create_notes_schema`.
3. Record the migration timestamp.
4. Leave `seed.sql` unapplied.

## 7. Verify migration history

```bash
supabase migration list \
  --db-url "$SELF_HOSTED_DB_URL"
```

The migration timestamp should now appear in both columns:

```text
LOCAL           REMOTE
<timestamp>     <timestamp>
```

Running the dry run again should report no pending migrations:

```bash
supabase db push \
  --dry-run \
  --db-url "$SELF_HOSTED_DB_URL"
```

## 8. Verify the deployed tables

```bash
psql "$SELF_HOSTED_DB_URL" \
  -c "\dt public.*"
```

Expected:

```text
note_tags
notes
profiles
tags
```

Inspect the notes table:

```bash
psql "$SELF_HOSTED_DB_URL" \
  -c "\d+ public.notes"
```

## 9. Verify RLS

```bash
psql "$SELF_HOSTED_DB_URL" \
  -c "
    select
      tablename,
      rowsecurity
    from pg_tables
    where schemaname = 'public'
      and tablename in (
        'profiles',
        'notes',
        'tags',
        'note_tags'
      )
    order by tablename;
  "
```

Every row should show:

```text
rowsecurity = true
```

Check policies:

```bash
psql "$SELF_HOSTED_DB_URL" \
  -c "
    select
      tablename,
      policyname,
      cmd
    from pg_policies
    where schemaname = 'public'
    order by tablename, policyname;
  "
```

## 10. Prove that seed data was not deployed

```bash
psql "$SELF_HOSTED_DB_URL" \
  -c "
    select
      (select count(*) from auth.users) as users,
      (select count(*) from public.notes) as notes,
      (select count(*) from public.tags) as tags;
  "
```

Expected:

```text
users | notes | tags
------+-------+-----
0     | 0     | 0
```

This is correct:

- migrations are deployable application structure;
- `seed.sql` is local development data;
- production users must be created through Supabase Auth;
- production data must not come from local fixtures.

## 11. Lint the deployed schema

```bash
supabase db lint \
  --db-url "$SELF_HOSTED_DB_URL" \
  --schema public
```

## 12. Clear secrets from the shell

When finished:

```bash
unset SELF_HOSTED_DB_URL
unset SELF_HOSTED_DB_PASSWORD
unset SELF_HOSTED_TENANT_ID
unset SELF_HOSTED_ENV
```

You should now see the four empty application tables in self-hosted Studio at:

```text
http://localhost:8000
```
